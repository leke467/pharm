# 30. Offline Price Changes

Price updates require special conflict rules.

- centrally managed price versions are synchronized to branches
- branches continue using the latest valid locally cached price while offline
- when the connection returns, synchronization reconciles the branch with the central version

# 37. Idempotency

Synchronization requests must be idempotent.

If a branch sends the same event twice because of:

- timeout
- network failure
- application restart
- server response lost

the server must not create two sales or two stock movements.

Every event needs a globally unique ID.

The server should safely recognize:

    event already processed

and return the existing result.

# 38. Offline Synchronization

        ->
    Upload pending events
        ->
    Download remote changes
        ->
    Apply changes
        ->
    Mark events synchronized

    Offline

# 39. Sync Retry Logic

The application must automatically retry failed synchronization.

Use sensible backoff.

Do not freeze the POS screen waiting for Internet.

The user should be able to continue working locally while synchronization happens in the background.

A temporary server/network failure must not make the pharmacy unusable.

---

# 40. Sync Conflicts

Conflicts must be explicitly designed.

Do not use blind "last write wins" for inventory quantities.

For example:

    Branch 1 offline:
        quantity 100
        sells 10
        local result 90

    Branch 2 independently:
        quantity 100
        sells 20
        local result 80

When synchronized, the system must not choose 80 or 90 arbitrarily.

Instead model the operations:

    SALE -10
    SALE -20

and derive the correct resulting stock according to the central inventory state and valid business rules.

Inventory should therefore rely heavily on movements/events rather than direct quantity replacement.

# 72. Time Handling

    ProductBranch relationship is created

    Branch 3 receives product master data
